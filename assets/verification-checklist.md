# 质量验证清单 — Verification Checklist

> 本文件定义需求分析结果的质量检查标准。
> Agent 在 Step 5 必须逐项检查，复杂场景自动触发 CoVe 二次验证。

---

## 一、检查时机

| 场景 | 检查方式 |
|------|---------|
| 所有场景 | 按本清单逐项自检（Step 5） |
| 复杂场景（>50 字或含并列连词） | 自检 + CoVe 二次验证（见第五节） |

**复杂场景判定**：`text.length > 50` 或匹配正则 `同时|此外|并且|另外|以及|且|不但|而且|不仅|还有|除此之外|另一方面`

---

## 二、5 锚点完整性检查

每条 FR 必须包含以下 5 个锚点，逐条检查：

| # | 锚点 | 字段 | 检查项 | 不通过时的处理 |
|---|------|------|--------|---------------|
| ① | 页面位置 | `uiLocation` | 是否明确到"XX页面/XX模块/XX区域"？ | 标记"待明确"，提示补充 |
| ② | 数据来源 | `dataSource` | 是否明确"根据XX配置/XX接口/XX条件"？ | 标记"待明确"，提示补充 |
| ③ | 配置方式 | `configurable` | 是否为布尔值且与描述一致？ | 补充 `true/false` |
| ④ | 默认状态 | `defaultState` | 是否为"默认开启"或"默认关闭"？ | 补充默认值 |
| ⑤ | 具体示例 | `example` | 是否包含真实场景举例？ | 补充示例 |

**通过标准**：所有 FR 的 5 锚点全部非空且语义合理。

---

## 三、6 段式完整性检查

| 段 | 检查项 | 不通过时的处理 |
|---|--------|---------------|
| 1. 业务背景 | 5 字段（提出方/问题层级/现状/解决层级/预期成效）是否齐全？ | 补充缺失字段 |
| 2. 总体需求 | 是否恰 1 条？是否含通用性考虑？ | 调整为 1 条，补充通用性说明 |
| 3. 功能需求 | 是否 2–6 条？每条是否为完整业务能力而非 UI 步骤？ | 合并过细项 / 拆分过粗项 |
| 4. 接口需求 | 是否存在？为空时是否标注"无"？ | 补充"无" + 解释文字 |
| 5. 数据需求 | 是否存在？为空时是否标注"无"？ | 补充"无" + 解释文字 |
| 6. 非功能需求 | 是否存在？是否标注硬性约束 vs 假设？ | 补充并标注类型 |

**通过标准**：6 段全部存在，空段有"无"标记，非空段内容合理。

---

## 四、CoVe 4 项质量检查

> Chain-of-Verification — 逐项验证需求分析的正确性

| # | 检查项 | 检查方法 | 发现问题时的处理 |
|---|--------|---------|-----------------|
| 1 | 幻觉需求 | 逐条 FR 回溯场景描述，是否存在场景中未提到的需求？ | 删除幻觉 FR |
| 2 | 遗漏功能 | 逐句扫描场景描述，是否有关键功能未被 FR 覆盖？ | 补充遗漏 FR |
| 3 | 过度拆分 | 每条 FR 是否代表完整业务能力？是否存在"显示XX页/输入XX/点击XX按钮"这类实现步骤？ | 合并为完整能力 |
| 4 | 逻辑一致性 | FR 之间是否矛盾？FR 与总体需求是否一致？数据流是否与 FR 对应？ | 修正不一致处 |

**CoVe 验证 Prompt**（发送给 LLM 进行二次验证）：

```
原始场景：
{sceneText}

初步分析结果：
{JSON.stringify(initialResult, null, 2)}

请逐项检查：
1) 是否有场景中未提到的幻觉需求
2) 是否有遗漏的关键功能
3) 是否有需求被过度拆分（粒度应为完整能力而非操作步骤）
4) 是否逻辑一致

有问题请修正后重新输出完整的 JSON 结果；无问题则输出与初步结果一致的 JSON。
```

**验证策略**：
- 先展示初版结果给用户（不阻塞）
- 后台执行 CoVe 验证
- 如验证结果与初版不一致，用验证后的结果更新展示
- 如验证无变化，保持初版

## 五、FR 粒度检查

| 粒度 | 示例 | 判定 |
|------|------|------|
| 完整业务能力 | "故障响应等级配置"、"行车组织建议管理" | ✅ 通过 |
| 子系统级能力 | "报警分级展示"、"处置建议配置" | ✅ 通过 |
| UI 操作步骤 | "显示响应等级标签"、"点击保存按钮" | ❌ 过细，需合并 |
| 系统级概括 | "报警管理系统" | ❌ 过粗，需拆分 |

**判断标准**：一个 FR 应该对应 Demo 原型中的**一张可独立演示的功能卡片**。

---

## 六、NFR 标注检查

| 类型 | 含义 | 示例 | 标注 |
|------|------|------|------|
| 硬性约束 | 必须满足，不可协商 | "系统需支持 1000 并发用户" | `【硬性约束】` |
| 假设 | 待验证的前提，可能变化 | "假设用户已安装 Chrome 113+" | `【假设】` |

每条 NFR 必须标注类型。

## 九、Demo HTML 代码生成检查（写入文件前必检）

> 对应 `prototype-template.md` §七 的 4 类防坑规则，写入文件前执行以下检查：

| # | 检查项 | 方法 | 不通过时的处理 |
|---|--------|------|---------------|
| 1 | `</script>` 转义 | `html.count("<script") == html.count("</script>")` | 外层闭标签必须为 `</script>`，仅 JS 字符串内的才可为 `<\/script>` |
| 2 | 无 `type="module"` | `'type="module"' not in html` | 改为 `<script>`，`file://` 下 module 受 CORS 拦截 |
| 3 | 无 `:class="{{"` 错误绑定 | `not re.search(r':\w+="\{\{', html)` | 改为 `:class="expr"`，`{{ }}` 仅用于文本插值 |
| 4 | Vue 已内联 | `vue.global.prod.js` 内联而非 CDN | 内联 `vue.global.prod.js`（~160KB） |
| 5 | Mermaid 降级 | `html` 中含"查看 Mermaid 源码"或等效降级 | 添加 `<details>` 源码降级，CDN 失败不致空白 |

```python
import re
assert html.count("<script") == html.count("</script>")
assert 'type="module"' not in html
assert not re.search(r':\w+="\{\{', html)
assert "查看 Mermaid 源码" in html
```
