# 需求表述规范 — Requirement Writing Guide

> 本文件定义需求文档"如何写得精准、可落地、可测试"的规范。
> Agent 在生成每条 FR 和每段文档时，必须逐项对照本规范。

---

## 一、6 段式文档结构

每份需求文档必须包含以下 6 段，**空段标注"无"而非省略**（避免下游误判为遗漏）：

| 段 | 标题 | 回答的问题 | 必填 | 为空时 |
|---|------|-----------|------|--------|
| 1 | 业务背景及目标 | 为什么做 | 是 | 不可为空 |
| 2 | 总体需求 | 做什么（概括） | 是 | 不可为空 |
| 3 | 功能需求 | 做什么（分解） | 是 | 不可为空（至少2条FR） |
| 4 | 接口需求 | 依赖什么外部系统 | 是 | 标注"无" |
| 5 | 数据需求 | 有什么数据约束 | 是 | 标注"无" |
| 6 | 非功能性需求 | 有什么质量约束 | 是 | 标注"无"或"待补充" |

### 6 段之间的关系

```
业务背景（为什么） → 总体需求（做什么-概括） → 功能需求（做什么-分解）
                                              → 接口需求（依赖谁）
                                              → 数据需求（数据约束）
                                              → 非功能需求（质量约束）
```

---

## 二、每条 FR 的 5 锚点

每条功能需求（FR）必须包含以下 5 个锚点，缺少任一锚点视为**不完整**：

| # | 锚点 | 字段 | 含义 | 反例（缺少锚点） | 正例 |
|---|------|------|------|---------------|------|
| ① | 页面/模块位置 | `uiLocation` | 在哪个页面的哪个模块/区域 | "新增响应等级功能"（没说在哪） | "在报警摘要处新增模块【响应等级】" |
| ② | 数据来源/触发条件 | `dataSource` | 数据从哪来、什么条件触发 | "显示响应等级"（没说根据什么） | "根据报警code配置，针对运营故障/运营风险" |
| ③ | 配置方式 | `configurable` | 是否支持项目级差异化配置 | 不提配置（下游以为是固定的） | `true` + "作为项目数据管理，支持按项目配置" |
| ④ | 默认状态 | `defaultState` | 初始是否启用 | 不提默认（下游不知道初始行为） | "默认关闭，选择启用时才显示TAB页" |
| ⑤ | 具体示例 | `example` | 一个真实场景举例 | 无示例（抽象难理解） | "郑州4号线轨旁ATP单系故障时显示蓝色预警" |

### 5 锚点对下游的映射

```
FR.uiLocation    → 原型：对应 Demo 中的卡片/组件位置
                   开发：对应前端路由/组件结构
FR.dataSource    → 原型：对应数据绑定/接口调用标注
                   开发：对应后端接口/API 设计输入
FR.configurable  → 原型：对应开关/TAB/下拉等配置控件
                   开发：对应配置表/后台管理功能
FR.defaultState  → 原型：对应初始展示状态
                   开发：对应默认值/初始化逻辑
FR.example       → 原型：对应演示数据
                   开发：对应测试用例 / 验收场景
```

## 三、可测试性

每条 FR 的 `description` 必须隐含**验收条件**，做到"可测试"：

| 原则 | 说明 | 示例 |
|------|------|------|
| 动词+宾语 | 以动词开头，明确系统要做什么 | "支持根据报警code配置响应等级" |
| 可量化 | 尽可能包含数量、条件、阈值 | "针对运营故障/运营风险两类报警"而非"针对报警" |
| 可验证 | 读完能想象出测试用例 | "默认关闭，启用后按code显示对应内容"→ 测试：关闭时不显示/启用后按code显示 |
| 无歧义 | 避免"快速/友好/智能"等无法度量的形容词 | 用"3秒内返回结果"而非"快速返回" |

### 安全/约束类 FR 的否定式表述

安全苛求类需求（如铁路信号）需用**"不XX"否定式**明确约束边界，每条都是可测试的验收标准：

```
✅ "不自动排列途经无网区段的列车进路"
✅ "进路经由分路不良区段时，须人工确认空闲方可办理"
✅ "不自动排列经由处于封锁状态的道岔的进路"
❌ "保证进路安全"（无法测试）
```

## 四、项目可配置性

新增功能需考虑**通用性 vs 项目定制**的平衡：

| 场景 | 写法 | `configurable` |
|------|------|---------------|
| 纯通用功能 | "系统支持XX，所有项目一致" | `false` |
| 项目可配置 | "作为项目数据管理，支持按项目/用户需求配置" | `true` |
| 可开关功能 | "默认关闭，项目选择启用时按code显示对应内容" | `true` + `defaultState: "默认关闭"` |

**原则**：当需求涉及"不同项目可能有不同规则/文案/阈值"时，标记为可配置，避免硬编码。

## 五、背景合理性

`businessContext` 5 字段的填写规范：

| 字段 | 含义 | 填写要求 | 示例 |
|------|------|---------|------|
| `proposer` | 谁提出的需求 | 具体到团队/角色，不写"用户" | "郑州地铁代维团队" |
| `problemLevel` | 哪个层级的问题 | 工班/车间/段/部/职能部门 | "段/部级（中高层管理）" |
| `currentState` | 现状如何处理 | 当前的 workaround，为什么不够 | "靠Excel表格手动维护台账，易出错且无法实时同步" |
| `targetLevel` | 解决到哪个层级 | 信息化/自动化/智能化 | "信息化 + 自动化" |
| `expectedBenefit` | 预期成效 | 至少1项可量化，关联降成本/降人力/提效率/提质量 | "减少80%手动维护工作量，数据准确率提升至99%" |

## 六、通用性设计

```
总体需求 需包含"通用性考虑"一句话：
  "考虑到产品功能的通用性，在XX处增加模块/配置，支持不同项目按需启用"

功能需求 需说明配置粒度：
  "故障响应等级数据作为项目数据管理，支持根据不同项目用户需求配置"
  "该TAB页配置项默认关闭，显示当前根据报警code配置内容"
```

---

## 七、文档完整性规则

1. **6 段必须全部出现**，空段写"无" + 一句话说明（如"本系统暂无外部接口依赖"）
2. **每条 FR 的 5 锚点必须全部填写**，空锚点写"待明确"并在验证清单中标记为待补充
3. **NFR 需标注类型**：`【硬性约束】` vs `【假设】`
4. **总体需求需包含通用性考虑**（一句话说明如何兼顾不同项目的差异）
5. **避免"无"段被下游误判为遗漏**：每个"无"后跟一句解释性文字

---

## 八、反模式

| 反模式 | 症状 | 修正 |
|--------|------|------|
| 悬空 FR | 只有标题和一句话描述，无5锚点 | 补充5锚点表格 |
| 形容词需求 | "系统应快速响应" | 改为"系统应在3秒内返回结果" |
| 隐式假设 | "用户会正确输入" | 显式写出假设并标注`【假设】` |
| 过度拆分 | 把一个完整能力拆成多个UI步骤 | 合并为一个FR，粒度对齐"可独立演示的卡片" |
| 遗漏空段 | 接口/数据段直接不写 | 必须写"无" + 解释 |
| 硬编码思维 | "郑州4号线显示蓝色预警"（写死） | 改为"支持按报警code配置，以郑州4号线为例..." + `configurable: true` |
